# Durable timers and civil calendars

`excalibur-scheduler` provides scoped timers over the shared storage writer: UTC one-shot and fixed intervals, civil one-shot times, and numeric five- or six-field cron expressions evaluated in an IANA zone. Calendar operations use the pinned Jiff library. Lists, ranges and positive steps are accepted; named months/weekdays and nonstandard cron extensions are not accepted. Five fields mean minute/hour/day/month/weekday; six add leading seconds. Sunday is 0 or 7. Restricted day and weekday fields combine with OR; a wildcard field combines with AND, including wildcard steps.

Civil inputs are local date/time values with whole-second precision. Offsets and zone annotations in that string are rejected because the separate IANA zone supplies the authority for conversion. A missing local time maps to the first valid instant after the gap (02:30 → 03:00 for a one-hour spring gap); an ambiguous time uses the first occurrence. A cron event in a repeated hour is delivered once. This intentionally refines Jiff's [compatible disambiguation](https://docs.rs/jiff/0.2.38/jiff/tz/enum.Disambiguation.html), which otherwise shifts a gap by its duration. Calendar searches are bounded to eight years and fail explicitly if no occurrence exists.

A tick atomically records intended UTC fires in a delivery outbox and advances each timer. Fire IDs encode scope, timer ID and intended UTC time. Calendar search completes before taking the writer transaction; a comparison against the original definition and cursor rejects stale plans after another tick or zone change. Competing ticks cannot duplicate fires. Creating the same ID with a different definition is rejected; recipe changes need a new ID, except for the explicit zone-change operation below.

Recovery applies `RunAll`, `RunOnceNow` or `Skip`. Bounded `RunAll` pages retain their backlog. `RunOnceNow` coalesces missed occurrences into the latest intended time; `Skip` advances without delivery unless an occurrence is due exactly at recovery time. Regular ticks record every due occurrence up to the page limit.

`change_timezone` recalculates an active civil timer, preserving the old/new definitions and an operation-keyed change notice in the same transaction. Due work must be recorded first: changing a timer with a due cursor fails instead of silently dropping missed fires. Completed one-shot timers are never resurrected. The returned notice includes old/new zone and UTC cursor; `timezone_changes` and acknowledgment support durable delivery by a host. Retrying a key reuses its original result even after time moves; conflicting arguments are rejected. Old pending fires keep their original IDs and UTC times.

Pending fires and zone notices survive reopening. Acknowledgment is scoped and idempotent. Consumers must honor a fire's ID as an external idempotency key: the outbox alone cannot make an external send atomic with acknowledgment. The authenticated host supplies scope; payloads cannot widen it. Schema versions 2 and 3 are additive and retains the original version-1 checksum and data.

Verification: `cargo test -p excalibur-scheduler` covers recovery, bounded replay, interruption, concurrent ticks, scopes, overflow, DST gaps/folds (including half-hour and date-line transitions), leap years, numeric cron, zone-change replay and version-1 migration. Fixtures are deterministic and local. The earlier UTC foundation's results do not substitute for checks of the calendar extension.

This remains a partial H9 library. Daemon dispatch and notification delivery, user tools/API, dependency/activity windows, reminder host integration, startup safe mode/quarantine, retention and signed installation/updates remain pending. No desktop/mobile client, external delivery or complete H9 operation is claimed.

Calendar search skips earlier field values rather than rescanning the day, and scheduler computations use a globally bounded two-job blocking executor. Hosts can supply their dedicated CPU runtime with `open_with_calendar_runtime`. Calendar exhaustion completes the cursor after persisting its final valid fire; it is distinct from invalid input. Regression tests count candidate visits for a late-day 1,000-fire backlog, exercise a blocked calendar job while the async runtime and writer progress, and preserve the last leap-day occurrence in year 9996.


## Reminder domain

`reminders::Reminders` is a host-only backend bound to authenticated scope, principal, conversation and optional source. Hosts supply these fields from authentication; model arguments and reminder text must never supply authority. The binding is sealed in the handle and persisted as a namespaced hash. Text, preferred channel and optional task links are inert data; channel metadata does not change global notification policy.

`apply` supports create, snooze, complete and delete. Mutations and bounded, keyset-paginated `list` snapshots require an operation key. Exact retries return the original response even after subsequent mutations or reopening; key reuse with different arguments fails. Snooze/complete/delete require the current generation and active state. Delete preserves a tombstone and history. Lists include tombstones. Text is bounded to 16 KiB, IDs and keys to 256 bytes, metadata to 512 bytes, requests to 64 KiB, and pages/ticks to 1–1000 entries.

The additive checksum-verified schema version 3 uses the existing database writer and timer/fire outbox. Calendar computation happens outside the writer; creating the reminder, timer binding and receipt commits atomically. Snooze atomically disables older cursors, records cancellation receipts for old undelivered fires, advances the generation, and creates the replacement timer. Completed/deleted reminders disable their cursors and cancel old pending fires. Cancellation never sets `delivered`; generic scheduler pending and acknowledgment exclude cancelled fires, while unrelated timer semantics remain unchanged. Reminder pending joins sealed timer bindings and the current active generation, rather than trusting payloads.

`Timing::Every` and `Timing::Cron` retain scheduler recurrence semantics: they continue producing intended occurrences until a lifecycle mutation stops them. This is **not** an unanswered-reminder repeat policy, delivery acknowledgment, or an infinite retry-until-answer implementation. One-shot reminders do not automatically repeat. The architecture requirement for policy-based repeats without a response remains pending host work, together with preferred-channel delivery, mobile system scheduling and user-facing tools.

A pending result is a snapshot. A future host must check the current active generation atomically with its durable notice receipt before an external effect, and use fire IDs for deduplication. This library does not implement that receipt or solve the race between an already-authorized external send and concurrent revocation. No notification delivery or daemon integration is claimed.

Verification: `cargo test -p excalibur-scheduler --test reminders` covers scoped authority, source isolation, exact replay, conflicting keys, pagination, stale generations, atomic rollback, pending cancellation, concurrent ticks/snooze, reopening and real child-process interruption. The interruption test kills continuing API mutations at an uncontrolled transaction boundary; injected SQLite aborts separately test rollback after reminder/timer changes. All fixtures are local.
