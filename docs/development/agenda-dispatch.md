# Explicit reminder dispatch core

`excalibur_daemon::agenda::Agenda` is a shared Rust host API. An authenticated host opens it with an accepted-client `HostNotificationBinding`, then calls `apply`, `list` and `tick_once`. It installs no background daemon service, RPC or model tool. The scheduler and notification sink use the orchestrator's existing main database; no second engine or delivery outbox is introduced.

The reminder namespace uses principal, scope and conversation with `source=None`. A later accepted source in that same namespace can list, snooze, complete or delete reminders. The original creator's accepted message binding is stored as opaque host JSON per generation. Scheduler schema 4 adds metadata and notification-condition tables without changing the checksums of schemas 1–3. Metadata, the generation CAS, timer cancellation and the operation receipt commit together. A losing CAS cannot overwrite the winner's metadata. Snooze and terminal generations inherit the creator binding. Legacy `Reminders::apply` retains its original operation request serialization.

Each explicit tick reads actual recovery status. It persists due fires while recovering or in safe mode, but queues no notices. Notice admission checks recovery status again inside the SQLite writer. A fire yields a SHA-256 key over a typed JSON tuple; replay uses the same original source binding, text, route and scheduled timestamp. The scheduler fire is acknowledged only after `notify_host_guarded` returns the durable notification receipt. This means **NotificationQueued**, not channel delivery or user acknowledgement. A process interruption between that commit and scheduler acknowledgement replays the existing notice.

A sealed generation/fire condition is checked inside the notification insertion writer. Complete, delete and snooze cancel old generations. The same condition and current accepted-source authority are rechecked when selecting channel attempts and inside the actual Master sink writer. The daemon uses `publish_notice_checked` and `flush_notices_checked` for this purpose; normal bucket publication checks each member again. Additive Master schema 6 stores the host-supplied notification origin in a sidecar, independently of notice JSON. This survives reopening. Legacy publication cannot replay a protected sink receipt, and legacy flushing retains protected rows without publishing them. Checked flushing rejects unknown origins, skips revoked members, publishes valid members, and counts only nonempty groups; cancelled members remain unflushed. Suppressed pending notices and attempts retain their durable receipts and are not newly reported delivered or acknowledged. A sink event committed before cancellation remains history; cancellation suppresses subsequent effects, including a not-yet-published normal bucket. A condition check outside the effect writer is only a snapshot and grants no in-flight delivery permit. Neither ordinary notification JSON nor a model payload can create a host guard or source authority. Hosts writing their own delivery adapters must likewise persist their effect conditions and use a transaction guard at their effect boundary; fetching pending rows is not authorization to deliver them.

This core does not implement automatic timer waking, dependency/after/window scheduling, reminder follow-up policy, task spawning, mobile scheduled notifications or Agenda model tools. It has no shell/task effects. It does not complete all of H9 or architecture sections 21.1–21.2.

Unbound legacy reminders remain pending and confer no delivery authority. Keyset pages let a tick skip those rows and revoked original sources without hiding later eligible reminders; the tick admits at most its requested limit. The public fire condition is serializable for host persistence but cannot be deserialized from model JSON.

Focused verification:

```sh
cargo test -p excalibur-scheduler --test reminders
cargo test -p excalibur-daemon --test agenda_dispatch --test host_notifications
cargo test -p excalibur-master --test recovery_contract
```

The tests use real local SQLite, Master and Orchestrator state, synthetic accepted inputs and an offline provider. The agenda subprocess helper exits after a committed notification and failed scheduler acknowledgement, then the parent reopens the database and checks exact replay and one sink receipt. Scheduler tests race metadata mutations against a shared generation CAS. Host tests cover concurrent ticks, source stability, safe-mode backlog, stale fetched fires and suppression after a queued notice is completed.
