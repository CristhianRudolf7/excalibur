# Host-origin notifications

The host Rust API `Orchestrator::bind_host_notification` creates a sealed target from a typed `HostNotificationBinding`: principal, original scope, conversation, accepted client message ID, and host-configured approved channels. The source must exist in `master_client_receipts` and belong to that principal, conversation and scope. The original scope must also belong to the existing master capability ceiling. This binds only the original accepted scope; it grants no access to another project and does not follow later conversation scope switches. There is no model tool for creating this authority. Host callers must authenticate these arguments; arbitrary model JSON must never be forwarded into this API.

Bindings are stored as typed JSON hashed with SHA-256 and can be enumerated by principal for future host-service recovery. `notify_host(target, key, class, text, preferred, at)` writes the existing `orchestration_notifications` row and its host-origin receipt in one SQLite writer transaction. Host notices have an empty legacy `agent_id` and an explicit `source_kind=host` receipt; they create no agent, task or engine run. The same key returns the original snapshot, including timestamp and initial acknowledgement, even after later acknowledgements. Changed authority, scope, text, class or preferred channel rejects reuse. Keys are bounded to 256 bytes; authority fields and channel names to 512 bytes; approved routes to 32; text and its JSON encoding to 60 KiB.

The owner chose a conservative least-privilege rule: authority must still be valid when delivery is selected and immediately before the local adapter publishes, not only when admitted. Source ownership, original conversation/principal/scope and the current master capability ceiling are revalidated from storage. `host_notification_authority` distinguishes `NotHost`, `Authorized` and `Revoked`; `host_notification_origin` remains immutable receipt metadata, not an effect authorization. A revoked notice is omitted from sendable attempts, remains durably unacknowledged with its receipt and any pending attempts intact, and does not prevent other authorized notices from progressing. Restoring the same authority allows original-key snapshot replay and pending delivery. Already delivered attempts remain delivered. This decision clarifies the owner's delivery contract; it is not described as an auditor-proven defect. The check does not make a concurrent revocation atomic with an in-flight publication, and no external adapter is added.

The preferred channel is a per-notice override of existing routing policy, accepted only from the binding's host-approved route list. It never edits conversation policy. This is trusted host configuration, not a cryptographic capability or a new channel adapter. The daemon implements local conversation delivery only; unsupported external attempts remain pending. Mobile, email and Telegram delivery are not implemented here.

Delivery reuses `pending_deliveries`, `confirm_delivery`, acknowledgements and `Master::publish_notice`. Scope comes from the host-origin receipt, an existing trusted recovery receipt, or the actual agent record, never from notification content. The notice template displays the projected envelope scope even without a worker. Quiet hours, urgent handling, normal five-second buckets and progress filtering retain their existing behavior. Urgent cross-conversation routing for host notices selects only conversations owned by the bound principal and publishes a generic link, without the original content.

This is the delivery foundation used by the Agenda reminder dispatch ([explicit core](agenda-dispatch.md) and [automatic runtime](agenda-runtime.md)). This page itself does not dispatch timers or consume pending reminders, and does not implement repeat-without-response, add UI, or schedule OS mobile notifications.

Verification: `cargo test -p excalibur-daemon --test host_notifications` exercises the actual local master sink, source/principal/scope denials, scope switches, live ceiling/source-owner revocation after polling, retained pending attempts alongside an authorized notice, ordinary worker JSON forging host/scope, concurrent keyed insertion, transactional rollback, per-notice route overrides, same-principal links, foreign-principal exclusion, durable database reopening and snapshot replay without workers. The rollback fixture injects a SQLite failure before receipt insertion; a separate real subprocess exits abruptly after commit, and the parent reopens the database, replays the key and delivers once. `cargo test -p excalibur-orchestrator --test correction_notifications --test startup_recovery`, `cargo test -p excalibur-master` and `cargo test -p excalibur-daemon --test source_authority --test service_supervision` cover adjacent routing, recovery and authority contracts. These commands are the verification plan, not a claim that they have already passed on this change.
