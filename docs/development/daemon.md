# Daemon, master and subagents

The daemon hosts the existing shared Rust engine. `excalibur-master` owns durable intake and bounded conversational turns; `excalibur-orchestrator` owns agent trees, mailboxes, admission, control and notifications; `excalibur-gateway` adapts those services to authenticated JSON-RPC. `excalibur-daemon` supplies the host lifecycle and the CLI stays a process adapter.

## Hosting and development

```sh
cargo build --workspace
# Supply a private, random bearer token of at least 32 characters through the environment.
excalibur daemon start --project /absolute/project --data-dir /absolute/private-data --listen 127.0.0.1:3791
excalibur daemon stop --data-dir /absolute/private-data --listen 127.0.0.1:3791
```

Both commands require `EXCALIBUR_DAEMON_TOKEN`. The start command runs in the foreground; a service supervisor can own its process. The principal database's exclusive ownership prevents a second owner. Relative data paths resolve once against the starting directory. SIGINT, SIGTERM and authenticated `daemon.stop` initiate shutdown. No installer, operating-system service registration or deployment is implied.

Without a model the daemon still receives durable messages and serves deterministic status/control; natural-language work remains pending with an availability notice. Configure an explicit model with `--model` or `OPENAI_MODEL` and its key through `OPENAI_API_KEY`; `--base-url` selects a compatible provider endpoint. A master fallback can be configured with `--fallback-model` or `OPENAI_FALLBACK_MODEL`, `OPENAI_FALLBACK_API_KEY` and an optional independent `--fallback-base-url`. Keys are read only when the corresponding model is configured and registered with the redactor. This fallback serves master turns; it does not silently change a worker’s model. The shared host also accepts explicit gateways and `MasterConfig`. The master uses the L0–L5 compiler with a 32,768-token ceiling that includes a ten-percent safety margin, 256 KiB and at most sixteen active turns. History is selected by scope before reading text; durable originals remain complete. A source that cannot fit produces `context_blocked`, without calling the provider or skipping it through a later message. The host can invoke `retry_context` after adjusting configuration, or stop that turn. Compilation and tokenization run in the background pool. Secrets are registered with the live redactor and are not included in client events. External model calls are unnecessary for the deterministic backend suite.

Explicit authenticated `/approve [id]` and `/deny [id]` commands use the same durable once-scope decision as `approval.respond`, without a model call. The ID must belong to a run originating in that conversation; omission selects only one unique pending, unexpired request. Ambiguity asks for the exact ID instead of guessing. Selection and its receipt are tied to the operation, so resending a message does not repeat the decision. Only an approval-waiting execution wakes, and user pauses remain paused. No approval-granting tool is exposed to the model.

The standalone adapter binds loopback. Remote hosting requires a trusted authenticated TLS reverse proxy; the shared router accepts host-provided explicit allowed Origins. Browser tokens must be sent in the Authorization header, never in a URL. See [gateway contracts](../../crates/gateway/README.md) for actual methods, blob authority and event cursors. Future memory, skill and automation methods are explicitly unavailable rather than simulated.

## Scheduling and authority

The host owns a two-thread interactive runtime, a separate work runtime and a bounded background CPU pool. Engine runs are Tokio tasks; tools retain their existing sandbox/process-group boundary. A panic at a turn, run or CPU-job boundary becomes a task error. A daemon background-service error initiates controlled shutdown instead of leaving the service silently inactive.

Each provider scheduler has four lanes and continuously replenished request/token buckets. P0 has one reserved concurrency slot and ten percent of the configured minute request/token quota; lower lanes cannot consume that reserve. FIFO order applies within each lane and a lower lane yields to queued higher lanes. Maintenance also yields while the host marks the user active. Reservations use the adapter's declared call bound when available, otherwise a serialized-request estimate. Host ceilings are reduced by numeric `x-ratelimit-limit-requests` and `x-ratelimit-limit-tokens` response headers observed by the compatible adapter; invalid values are ignored. No quota is inferred when headers are absent, and traffic outside this installation is not accounted for. Header names follow the [official OpenAI rate-limit documentation](https://developers.openai.com/api/docs/guides/rate-limits). Priority wrappers preserve observed provider metrics and cache/replay metadata.

The Linux host reads daemon and descendant RSS from `/proc` each second. The shared resource controller stops admission, requests idle-resource unloading, pauses low-priority runs for resources, and can stop a tool as the final action. Admission resumes after sixty seconds below eighty percent of the configured limit; user pauses remain paused. Native RSS adapters on other platforms are explicitly unavailable in this adapter. Linux tools and background runtime threads use `max(current nice, 10)` so a host already running at lower priority is never promoted; tool processes also request best-effort I/O priority 7. An optional trusted `HostOptions.cgroup_root` / `--cgroup-root` must be a real cgroup v2 directory with the CPU controller already delegated to children. The host creates a stable separate child per execution (including its checks), verifies `cpu.weight` as `min(10, parent weight − 1, observed daemon weight − 1)`, and places tool children there before executing user code. It never changes controllers or moves the daemon. Invalid explicit delegation fails closed; without it, nice/ioprio apply. Delegated root provisioning and final empty-group removal belong to the service manager. Native tests read effective nice, I/O priority, CPU weight and host-side process membership; sandbox cgroup namespaces do not expose host paths.

`HostOptions` supplies canonical root authority and registered projects. Each project root must lie inside that authority. `DaemonActions` narrows a project's worker paths and data scopes; `Security::register_run` checks every actual child token against its parent before dispatch. The master role exposes only bounded coordination/status/question/time operations. File and terminal work becomes a level-one run. Workers at level two cannot create children, even by calling a hidden tool directly. Profile catalogs are frozen in each run's durable context; runtime authorization remains independent of tool visibility.

The `general` scope excludes registered project files, including in the verifier. Select the initial project using `scope: "project:default"` in `conversation.send` or `/project default`. Registering project metadata does not widen the permission ceiling: executable scopes and authorized roots are provisioned in `HostOptions`. Registered custom profiles retain a mandatory base role; names, icons and identity text cannot add permissions.

The host can configure `GitOptions` with a real identity and `IntegrationChecks`; no defaults are invented. The parent creates the registered worktree and a child delegation carries `worktree-owner:<owner>` in `inputs`. The host checks parent task, scope, canonical root and unique ownership, fixes the effective token and routes files/processes to that tree. Child checkpoint and Git queue operations use their specific authority; integration remains the parent's operation. A2 can require an actual Git approval; A3 needs explicit `full_acknowledged`. The CLI does not invent an identity or integration checks. `ScopedPlanning` reuses `EpisodeTools` transactions and receipts; each run's completion gate and independent verifier use its effective root.

## Durable coordination

Intake persists before acknowledging and deduplicates by client identity and `client_msg_id`; a conflicting reuse is rejected. A client's outbox may resend an unacknowledged message and resume events using the last confirmed cursor. Conversations run independently; each conversation serializes its turns, limits them to eight model steps and injects queued messages at safe boundaries. Early unshown generation can restart with the combined messages. Provider failure retains the inbox and keeps status/control available; half-open attempts continue with a bounded exponential interval while real requests remain pending. Each primary and fallback attempt has its own deadline. One deterministic unavailability notice is persisted per outage episode; recovery schedules the retained inbox and conversations received during the outage. Explicit status/control commands bypass the ordinary per-scope inbox capacity.

Structured delegation carries goal, deliverable, scope, paths through the capability token, input references, literal instructions, skills, budget and optional explicit context fork. A child normally receives no parent reasoning/history. Every task retains a durable request card with literal source messages and their IDs, interpretation, instructions, assumptions and an initial observable criterion. Child budget reservations are enforced by the existing durable engine. `task_db` and `task.batch` share a durable outbox that propagates only confirmed corrections to affected branches; task revisions invalidate their evidence. Waiting parents release execution slots, allowing children of several trees to advance under the global running limit. Model-callable coordination tools and the completion gate use the same orchestrator as the API.

Mailbox messages have durable IDs, at-least-once delivery and explicit acknowledgments. Directives persist before delivery, propagate only to affected branches/scopes and retain their instruction revision. The engine and tool cancellation contracts determine when interrupting is safe. The status projection reads durable state, outstanding model/tool intents, host live output, usage, queue position and narrative reports; it cannot reveal a model's private generation or progress inside a silent tool.

Control commands are serialized and durable. Pause cascades with an operation-specific `paused_by`; resume restores only those descendants. Interrupt preserves unrelated descendants. Automatic pause/resume checks ownership reason and journal revision with CAS to preserve user pauses. Directive and resource resumes also wait for the run boundary, so a user pause issued during an in-flight effect wins. A committed approval decision resumes only the exact `approval required` pause without waiting for live inference; the engine re-checks a decision that commits while it is pausing, so no wakeup is lost. Check runners keep polling their execution while reading run status, so verification never stalls behind its own queued store read. Cancellation is terminal and requires authenticated confirmation; a model-generated boolean is not user confirmation in the master adapter. Redirect carries the new instruction and can resume the addressed paused run. Reversibility continues to use file history and shadow snapshots; a control command does not undo an already-sent external effect.

Notifications retain origin, class, delivery attempts and acknowledgment. Urgent notices bypass normal grouping; normal notices are collected into durable five-second windows and simple updates use bounded text templates without a model call once the conversation has no active turn. Quiet hours accept an IANA timezone and follow its daylight-saving rules. Origin conversations always retain their notice, urgent notices can link another active conversation without opening a turn there, and preferred external-channel attempts remain pending until a host channel adapter confirms an idempotent send. The standalone host publishes conversation notices; it does not claim a Telegram/mobile channel is installed. Acknowledgment in one channel suppresses subsequent attempts elsewhere.

## Verification

```sh
cargo test -p excalibur-master
cargo test -p excalibur-orchestrator
cargo test -p excalibur-gateway
cargo test -p excalibur-daemon
cargo test -p excalibur-cli --test daemon
cargo test -p excalibur-tools --test process_priority
cargo fmt --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo build --workspace
```

Tests use synthetic model responses, isolated temporary databases, native local sockets/processes and explicit time samples or paused Tokio time. Availability, steering, control and notification fixtures are backend tests. Platform execution evidence and any inherited pending items belong to the separate delivery report; a successful Linux test does not certify another operating system.

Worker journal progress shares the durable conversation event cursor. Entries expose only run, agent, scope, journal sequence and event kind; detailed state stays behind authenticated status queries. Replayed projections deduplicate by run and journal sequence. Each worker uses the same telemetry projection as embedded execution and exports per-run ATIF trajectories and metrics under `daemon-logs/runs/<run_id>`. Master attempts retain actual primary/fallback metadata, known cost/cache usage and pending unknowns.


## Explicit project actions

A master delegation can name `scope`; `scopes` records an explicitly transversal task. The primary scope must occur in that set. An override requires an unambiguous project mention in the frozen literal source messages and must fit the host token. The durable authorization receipt retains the original source IDs and text, so a later selector change cannot retarget replay. Separate project jobs receive separate tasks. A transversal job keeps one primary task scope and the exact granted project scopes and roots in its capability; it cannot acquire an unmentioned project. Git worktrees remain project-specific.

Master `task_db` operations may explicitly name different authorized scopes. The adapter validates every group before the first effect, executes one idempotent transaction per scope and returns labeled `scopes` results. This is not a cross-scope atomic transaction; retry uses the same group receipts. Unknown or ambiguous project mentions require clarification rather than a guessed write.

For write authorization, short ASCII aliases (one or two characters) use the explicit `project:<id>` spelling; an ordinary article is not a project grant.


Transversal workers bind a positive filesystem boundary to the exact registered root union. File reads/edits, searches, shadow captures and confined processes share that boundary; the independent verifier keeps it read-only. Ungranted nested projects and future files outside the union remain inaccessible. Historical captures with paths outside the current boundary cannot be listed or diffed through that run. `ToolRuntime::filesystem_confinement` is a trusted host attestation, absent by default: generic runtimes still require permission for the whole workspace. Every attested root is checked against the current token; model arguments cannot create an attestation.


Informational reports addressed to the master enter the same notification routing as other notices. `NotificationPolicy.progress` may be omitted/null (enabled by default for N3 tasks), true (enabled) or false (disabled). A valid task `notification_policy` overrides the conversation fields; malformed overrides preserve the conversation policy. Quiet hours and acknowledgments still apply. Required human answers, approval pauses and budget stops are urgent; ordinary child/tool waits do not generate repeated notices.


At a stopped-host startup, `DaemonHost::open` uses `Orchestrator::rebind_master_at_startup` to apply the trusted root ceiling from `HostOptions`, retaining the master ID and every existing descendant's frozen token. Ordinary `register_master` remains strict. Factories and grants use the current provisioned projects; all durable registered roots, including omitted projects, remain privacy denials for General and overlapping scopes. A run whose scope is no longer provisioned blocks before inference or tool effects and emits an urgent notice and parent message. The backend does not perform hot root or scope grants.

Availability verification uses `cargo test -p excalibur-daemon --test availability -- --nocapture`: authenticated HTTP receipt/status samples under zero, four and eight occupied work threads plus the same number of real sandboxed native C compilation loops. On Linux the fixture allocates up to four allowed CPUs to its inherited runtime/tool threads; loaded cases saturate that bounded allocation. It reports local p50/p95 against the suite’s two-second threshold. `cargo test -p excalibur-daemon --test end_to_end` compares daemon/embedded-exec output bytes, final state, ATIF tool names/arguments and successful effects, then independently reopens the episode’s persisted SQLite evidence. Exec trials require fresh directories; this check does not imply an exec-resume command.

`cargo test -p excalibur-tools --test process_priority -- --nocapture` checks effective Linux nice/ioprio and inherited nice 15. `EXCALIBUR_TEST_CGROUP=/explicit/delegated/root cargo test -p excalibur-daemon --test cgroups -- --nocapture` verifies distinct real execution cgroups; the same variable enables the real membership/weight test in `process_priority`. Without a usable CPU delegation those conditional checks explicitly report unavailable; ordinary directories are always rejected as cgroups.

Memory-pressure termination preserves a typed `memory_exhaustion` session reason and a failed tool observation with `terminated due to memory exhaustion`; the error survives later reads, rather than being inferred from a generic signal exit code. The native process test checks the actual selected largest group and an unaffected live group.


## Control, admission and source authority

Only literal authenticated client inputs and explicit human answers in `master_user_sources` can authorize another project. Generated questions, defaults, worker output and notifications remain context, never project grants. Cached grants and ancestor grants are checked again before dispatch. Additive checksum-verified migrations retain existing receipts and source text; an unverifiable grant blocks before model or tool effects.

Fast responses expose human-readable summaries rather than serialized capability tokens. Ambiguous cancellation returns candidates and requires a selection. In mixed control/work input the control executes once and the literal remainder stays queued with its original source. Strict time and canonical-ID recognition avoid treating ordinary file/version text as targets. Question limits apply to each originating client message, not the lifetime of a conversation.

Task creation assigns requirement and criterion codes within the same writer transaction that resolves the request card references. Cards retain the exact original inputs, actual `R#`/`C#.#` codes and literal constraints pinned into the worker instructions. Replaying a request retains its task and source receipt. Model-originated clarification defaults cannot make a mutable execution optional: only a read-only, process-free capability with no external actions can use the optional path. Optional worker questions default after fifteen minutes only at an idle wait; mandatory ones remind every twenty-four hours until answered. Defaults are durable assumptions, not user statements.

Admission defaults to eight running workers, four admitted children per parent, measured native process capacity (available CPU count by default), and eight provider worker slots. A fifth child remains durably ready in the queue; waiting parents release running slots. `Limits.project_weights` supports weighted project scheduling (weights 1–100). The model gateway additionally reserves a ninth slot for P0. Actual process/provider counts and estimates constrain new admission; these are admission budgets rather than per-run operating-system process quotas.

On memory pressure the host stops new admissions and unloads idle registered LSP/model resources, then pauses one lower-priority run per sample, starting with maintenance. Sustained severe pressure can terminate the largest live tool of a resource-paused run. Its result is an explicit memory-exhaustion failure. Remote model adapters have no local weights to unload and return zero; hosts can implement `ModelGateway::unload_idle` for actual resident resources. `HostOptions.project_services` registers project intelligence whose idle servers can be stopped. Hysteresis resumes only resource-owned pauses. Repeated user pauses preserve descendant ownership; direct cancellation of queued, waiting or paused children emits the same durable completion and budget settlement as reaping, once.

Directive acknowledgment clocks begin at delivery and count execution time rather than queue, pause, restart downtime or an already-running graceful tool. Status includes bounded tool argument summaries and elapsed intent time. A due narrative report reminder enters the actual L5 worker context. Background service iterations retry transient failures with bounded backoff; panic or a main writer failure signals controlled host shutdown. Shutdown drains or cancels in-memory workers and native processes even if persisting the final state fails.

## Focused backend checks

`master/tests/recovery_contract.rs` covers recovery beyond three failures, independent fallback deadlines, full-inbox control, source provenance, per-input clarification limits and durable grouped notices. `daemon/tests/provider_recovery.rs` exercises automatic recovery and a full inbox through the real foreground daemon and authenticated HTTP with a local compatible provider. `source_authority.rs`, `request_card_codes.rs`, `service_supervision.rs` and `idle_resources.rs` check dispatch grants, transaction-assigned cards, writer/panic shutdown and resident-resource unloading. Orchestrator `correction_*` suites cover control, settlement, weighted admission, clocks, question defaults, migrations and IANA quiet hours. Gateway listing tests include nested ignore rules and pagination beyond 10,000 entries. These checks use synthetic data and no external credentials or inference.

`cargo test -p excalibur-daemon --test native_multi_tree` exercises three authenticated conversation commands against three agent trees. A confined C check reads the original export-file bytes before a causal release gate; a separate native General process stays live. A versioned R4 update interrupts the affected pre-effect edit, reaches the running check with normal priority, and produces one real CSV edit. The completed native check remains trusted evidence of the original snapshot and cannot satisfy the changed criterion. Exact edit approvals use the authenticated approval API. Local pure-read barriers exercise immediate/cooperative cancellation contracts for the thesis tree; they are not browser/web adapters. The native workload is bounded and does not represent an eight-minute suite or external inference.

Check supervision polls execution and its durable control read concurrently, including while the bounded foreground SQLite reader is busy. A queued state read therefore does not suspend the execution future that must release that reader. `cargo test -p excalibur-tasks --lib concurrent_reader_polling` exercises the causal reader handoff with paused virtual time and real SQLite reads.
